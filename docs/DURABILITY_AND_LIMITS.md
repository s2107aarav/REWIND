# Durability and practical limits

Atomic writes use an exclusive random temporary file, file fsync, same-directory rename and attempted parent-directory fsync. Chunk data is written to two configured roots before manifests and commit markers. Existing hashed objects are read/hashed; capture fails on corrupt existing copies rather than repairing them invisibly. Both referenced datasets and manifests are complete before publishing the first marker. Markers publish A then B; no cross-backend atomicity exists. A single committed backend is sufficient for independent recovery if its bytes remain intact. Missing/invalid counterpart metadata is surfaced as degraded.

SQLite uses WAL and synchronous FULL for catalog transactions. It is derived, not durable truth. `rebuild-catalog` reconstructs snapshot/entry/ordered-reference tables from verified committed manifests. Damaged database files are retained with a `.damaged-<time>` suffix when rebuild detects corruption. The object/manifest format requires no SQLite database to rebuild.

Only filesystem/OS guarantees are available. Fsync and rename do not defeat faulty controllers, dishonest caches, disconnected media or power failure on every filesystem. Unsupported directory-fsync errors are tolerated on platforms that do not support them. Supported ordinary mode bits and mtimes are attempted; perfect ACL, xattr, resource-fork, sparse-file, ownership and hardlink preservation are not provided. Hardlinks capture as independent regular files. Source symlinks, devices, pipes, sockets and observed mount boundaries are skipped and reported. Nonportable filenames fail capture with a useful error.

Live directory scanning is not a single instant. Per-file identity, size, mode and mtime are checked before/after reading; metadata-only ctime changes require a second independent matching byte read. This was necessary on the observed iCloud workspace, where system xattr changes altered ctime without changing content. Directory identity and metadata are checked too. Obvious source changes abort capture. Files can still change after validation; coordinated application consistency requires application quiescence or OS snapshots, neither provided here.

Restore stages on the destination filesystem, hashes each chunk and full file, independently re-reads the staged output, then publishes with an **atomic exclusive native rename**. The packaged helper uses `renameatx_np(..., RENAME_EXCL)` on macOS and `renameat2(..., RENAME_NOREPLACE)` on Linux. An existing target, even an empty directory created concurrently, cannot be overwritten. Competing publishers have one winner. Unsupported OS/filesystem primitives fail closed with no unsafe rename fallback. Source builds need a C compiler; the desktop package includes the small compiled executable outside ASAR and requires no runtime compiler. Existing destinations are also rejected before reconstruction. Symlink components are checked, regular files use O_NOFOLLOW, and portable case/reserved-name collisions are rejected. Path ancestors must still be privately controlled: defeating an actively malicious local process that rewrites directory ancestors between checks is outside the v1 trust model. There is no in-place overwrite flow.

A crash before snapshot commit leaves orphan objects/manifests; they are not listed as snapshots. A crash after marker A can expose a complete degraded snapshot; after catalog loss it remains rebuildable. There is no unsafe GC/cleanup button. Orphan chunks consume space and are included in measured physical accounting.

A restore crash before publication leaves a named stage and intent; a crash after publication but before receipt leaves a verified-looking output that must be independently checked using `reconcile`. No successful receipt is fabricated. Retry requires a new destination and never overwrites the existing one. Stages/intents are retained and surfaced in warnings. The CLI provides independent verification and safe reconciliation, not automatic deletion of recovery evidence.

Health status records the last scan time; it may become stale immediately. No background watcher or automatic claim of ongoing integrity exists. Restore re-reads/re-hashes physical bytes. Backend unreadability is uncertainty, not evidence of permanent loss. Deep scans may become inconsistent under concurrent failures; current failures are rechecked conservatively, and future failures are never guaranteed away.

Two directories on one disk are independent logical copies only. They do not protect against disk failure, filesystem loss, shared credentials or malware. The laboratory uses ordinary physical copy operations without hardlinks/reflinks, so later lab writes do not alter the original file inode. Availability and I/O faults in a lab provider are simulations; chunk/manifest damage mutates actual copied bytes.

Laboratory mutations serialize with a lab-local lock and select intact copies using the seed plus persisted action count. Explicit repeated chunk damage is rejected; manifest damage writes a fixed invalid marker and cannot reverse itself. A successful physical mutation is followed by atomic scenario publication; these two filesystem changes are not one transaction. A crash or journal-write failure between them can leave unrecorded damage. The call reports failure, does not append an in-memory APPLIED action, and replay cannot reproduce that unrecorded mutation. Recreate the disposable lab from originals after such an error. Old v1 scenarios containing repeated ineligible chunk faults fail clearly during replay.

Suggested recovery always obtains a new deep scan through the desktop service. It distinguishes the newest complete snapshot from newest individually verified file versions across history. The latter may be application-inconsistent, are not automatically restored together, and remain evidence from scan time. UI scope/repository changes, operations and changed scan IDs invalidate the displayed recommendation.

Data is stored unencrypted locally. REWIND contains no telemetry, remote fonts, account, cloud API or required network requests. A user-selected source/store/workspace can be inside an OS-synced folder such as iCloud Drive; the operating system may sync it independently. Choose unsynced directories for a strictly offline storage policy. Version 1 targets accidental corruption/availability faults, not malicious rewriting of data and expected digests together.

Validated on this macOS arm64 host only. CI is configured for Linux and macOS; configuration is not evidence that external CI has run. Windows portability is conservative filename/path handling, not a claim of Windows validation. The macOS package is unsigned/unnotarized and uses Electron's default icon; distribution signing and installers are outside the executed local packaging gate.
